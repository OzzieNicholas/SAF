# 工程规范

代码、测试、产物、路径、文档和命名的统一约定。能机检的规则由 `tools/check_structure.py` 执行（由 `tests/acceptance/test_governance.py` 在测试和验收门里调用），其余靠评审。

## 1. 代码

- Python 文件和包目录使用小写 `snake_case`；不得用阶段号、日期或版本号作文件名前缀。
- 依赖方向固定为：`src`（产品代码）← `experiments`、`tools`、`paper`（执行适配器与论文下游）← `tests`（验证与门）。`src` 不得导入后者。
- 模块里的实质代码放在语义命名的文件中，`__init__.py` 只做导出和一句话说明。
- 重依赖（numpy、scipy、torch）尽量在函数内导入，使仅需要部分功能的调用方不被拖入整个栈。
- 新模块必须有至少一个消费者或检查；删除模块时同步删除消费者、测试和文档引用。
- 不保留无效的兼容分支、被舍弃的逻辑和临时目录。

## 2. 测试

- 验收性质放 `tests/acceptance/`，文件名 `test_*.py`，必须提供 `checks()` 供 `tests/gate.py` 汇总；同时提供 pytest 用的 `test_*` 函数。
- 单元测试放 `tests/unit/`，论文流水线测试放 `tests/paper_pipeline/`。
- 验收状态有四种：PASS、FAIL、PENDING（所需外部输入尚未生成）、N/A（经检验判定为非不变量或已被他处覆盖，可见、附理由、不阻塞完成）。`SkipTest` 只用于外部数据或可选环境缺失，可裁决的失败必须抛出，不能用跳过隐藏回归。
- 门是棘轮：已绿的性质不许静默退绿。

## 3. 路径与产物

- 仓库内不出现盘符绝对路径。数据位置只通过 `support_accessibility.runtime.data_paths` 取得，配置在 `configs/paths.yaml`；机器相关的覆盖写在不入库的 `configs/paths.local.yaml`。
- 机器结果写入 `artifacts/runs/`，并带运行记录信封（run_id、输入摘要、命令、工具版本）；检查点、日志、候选图和临时数组写入 `artifacts/cache/`。不得把缓存路径写进结果账本。
- 缓存由 `python tools/prune_artifacts.py` 清理：默认只列出，`--apply` 才删除超过 TTL（默认 7 天）的文件，且永远不触碰 `artifacts/runs/`。需要保留的结果先提升为证据再清理。
- 数据、`artifacts/`、论文 PDF 和构建目录不入库；论文成品图和小型证据清单入库。

## 4. 文档

| 项目 | 规范 |
|---|---|
| 语言 | 中文陈述；专有名词和术语可用英文 |
| 内容 | 详细、不遗漏关键点；措辞通俗易懂；不冗余，不在多处重复同一信息（用指针） |
| 禁止 | 日期、版本号、流水账式记录；遇到已有的要删除 |
| 结构 | 子标题层次明确：同级表示平行，下级表示归属，便于增删调整 |
| 辅助 | 适当使用表格和 mermaid 图 |
| 引用 | 有参考资料的内容做必要标注 |
| 命名 | 文档文件名用含义清晰、无歧义的中文（`README.md` 除外）；同一目录下的文档命名形式一致、长度相近 |

## 5. 文件与目录命名

- 以语义为主：不得用 `123`、`v1`、`cli`、`case` 之类无意义或有歧义的名称，要能从名字完整理解用途。
- 同一层次、同一类别的命名形式统一（都用单个词，或都用 `xxx_yyy`）。
- 发现既有内容或命名不符合以上规则，及时修改。
- 阶段号（阶段 0–10，见研发路线）和假设号（H1–H5，见研究背景与设计）只是逻辑标签，用在决策台账和结果账本里，不出现在文件名中。
